# Zero Agent: X調査 → AIキャラ選択 → SeaArt (Android直接操作) → 投稿待ち

## Android直接操作（試験実装）
- Xの画像解析で取得した推定いいね数から、AIがオリジナルアニメキャラ案・SeaArt用プロンプトを作成する。
- 「AndroidでSeaArt生成を開始」からChromeでSeaArtを開く。
- Zero Agentのアクセシビリティサービスが有効で、SeaArtの画面が認識できれば、入力欄にプロンプトを設定し、明確な「生成」ボタンを一度だけ押す。
- ログイン、モデル選択、料金確認、完了待ち、画像のダウンロード・自動保存はまだ実装していない。画面変更で動かなくなる場合は自動操作を中止し、手動操作・画像取り込みを利用する。
- 完成画像を「SeaArtで作った画像を保存（投稿待ち）」から取り込むと、端末内で ready_for_post_review にする。
- 投稿は行わない。

## 注意
- SeaArtのUIは変化する。現在の実装は実機未検証。
- 画像生成にはSeaArt側でクレジットが消費される場合がある。ユーザーが生成開始を押した場合だけ操作する。
- Bridge/Python/サーバーは不要。以前の tools/seaart_bridge.py と SeaArtBridgeClient.kt は削除済み。
- 保存済みの古いBridge設定値は利用しない。

## モデルとLoRA（2026-11）
- 新規AIキャラ案のSeaArt基本モデルは **GR-Illustrious 3in1**。
- キャラごとに任意のLoRA名を入力・保存できる。AIはLoRAの系統を提案できるが、実在するSeaArt LoRAのIDや互換性を保証しない。
- 現状、ChromeのSeaArt上でモデルとLoRAを選ぶ操作は未実装。生成前にユーザーがSeaArt上でGR-Illustrious 3in1と選んだLoRAを確認する必要がある。
- 画像はスクリーンショットではなくSeaArtのダウンロードボタンで元ファイルをダウンロードする。Chromeのダウンロード完了とアプリ内の投稿待ち登録を自動連携する処理は未実装。現状はダウンロードしたファイルをファイル選択で取り込む。

## ダウンロードの自動取り込み
1. アプリの「ダウンロードフォルダを選択（初回のみ）」からChromeの保存先を指定し、読み取りアクセスを許可する。
2. SeaArt生成開始時刻以降（5秒の許容幅）に保存され、ファイル名に `seaart` が含まれるPNG/JPEG/WebPを候補とする。サイズは8バイト～20MB。
3. 1件だけ一致したときのみ投稿待ちデータの対応するdraft IDにコピーして `ready_for_post_review` にする。元のダウンロードファイルは削除しない。
4. 候補が0件、複数件、アクセス不可なら自動登録しない。画面の手動取り込みを使用する。
5. ダウンロード操作後、アクセシビリティサービスは最大3分間、5秒間隔で取り込みを試みる。アプリに戻った際や「照合して自動取り込み」ボタンでも再試行できる。

注意: Chromeが生成ファイルを `seaart` を含まない名前で保存する場合は照合できない。ファイル名・更新日時だけでは内容の真正性は証明できないため、投稿前に画像を必ず確認する。Android SAFプロバイダーによってはダウンロードフォルダの選択や更新日時の取得が制限される。

### 根本原因候補・既存の修正
- `AccessibilityNodeInfo.ACTION_CLICK` が true でも、Webページの実際の画面遷移が完了した保証はない。
- `Img2Img` という文字だけで「創作画面に到達」と判定するのは誤り。
- PR #64（commit `e48d447a939a832de58a5e67f62f39776067c7a9`）で、画面下部の「創作」ノードを探し、クリック不可時はそのノードの矩形中央へ `dispatchGesture` でタップ、`/create/image` 遷移を確認する状態 `awaiting_create_navigation`、6秒後の再試行、`seaartLastError` 診断表示を追加した。
- PR #63 で SeaArt モバイル画面のモデル表示 `CivEdgeMix` と、紫のクレジット表示付き生成ボタンに対応を試みたが、**実機検証は未完了**。

### 次の作業で必ず確認すること
1. 最新APKのCIビルド成否、Androidのアクセシビリティ権限と Chrome イベント受信を確認。
2. `awaiting_create` → `awaiting_create_navigation` → `awaiting_editor` の状態遷移を時刻付きログに残す。実際のChrome URLとクリック対象のテキスト・矩形・ACTION_CLICK成否・dispatchGesture成否を記録し、誤判定を防ぐ。
3. 画面下部「創作」のノードが見つからない場合、Accessibilityノード階層・コンテンツ説明・WebViewの状態を調べる。フロートが重なっていないか確認。
4. 画面遷移の確認後にだけプロンプト入力、**GR-Illustrious 3in1** モデル選択、キャラに応じた LoRA 選択、生成を実行する。
5. 生成回数（1〜20）、ダウンロード、投稿待ちへの画像取り込みまで一貫して検証する。生成にはクレジット消費があり得るのでユーザーが指定した回数を超えて押さない。
6. **ユーザーの実機で創作タブが押せたことを確認できるまでは「修正済み・成功」と報告しない。**
